# v2.1.0 真实场景测试用例

## 测试目标

验证 RuntimeContract foundation 在真实本地后端、真实 runtime persistence 和 Web 控制台下可重复读写，并确认 System Validation 页面具备稳定自动化锚点与 checkpoint 安全 readout。

## 前置条件

- 已启动启用 runtime persistence 的 Athena 后端。
- 已执行 `go run . migrate`。
- Web 控制台已启动，并能访问同一个后端。
- 若执行 DOM 路径，本机 Python 环境已安装 Playwright 与 Chromium。

## API 验证步骤

1. 确认后端健康：

```bash
curl http://127.0.0.1:8090/healthz
```

预期结果：返回健康状态。

2. 执行 RuntimeContract foundation smoke：

```bash
python3 scripts/control_plane_runtime_foundation_smoke.py --base-url http://127.0.0.1:8090
```

预期结果：

- `status` 为 `ok`
- `foundation.contracts` 大于 0
- `foundation.task_types` 大于 0
- `foundation.hook_bindings` 大于 0
- `foundation.active_system_truths` 大于 0
- `foundation.system_truth_sources` 大于 0
- `foundation.system_truth_drafts` 大于 0
- `foundation.system_truth_compile_results` 大于 0
- `inspection_task`、`integration_event`、`scheduled_job`、`workflow_step_request` 均具备 active registered task type validator contract，且 validator status 为 `ready`
- `records.steps`、`records.lifecycle`、`records.traces`、`records.usage`、`records.projections` 均大于 0
- 每条 projection candidate 的 `schema_version` 均以 `runtime_projection.` 开头，`materialization_target.core_materialization_scope` 均为 `projection_candidate_only`
- projection candidate 的 kind、schema、materialization target 和 typed semantic payload 均不得声明为业务 `EvidenceRecord`
- `records.checkpoints` 存在且为数字；当有 checkpoint 时，返回项不得包含 raw `payload` 或 `resume_token`

## Web 验证步骤

1. 启动 Web 控制台并指向同一个后端。
2. 执行 DOM smoke：

```bash
python3 scripts/control_plane_runtime_foundation_smoke.py --base-url http://127.0.0.1:8090 --web-url http://127.0.0.1:5173
```

预期结果：

- `status` 为 `ok`
- `web.dom` 为 `ok`
- System Validation tab、Runtime Persistence Readout、checkpoint 安全摘要、Runtime foundation snapshot、System Truth lifecycle readout、Validator Contracts readout、Projection Boundary readout、capability surface、编辑器和验证按钮都能被稳定定位。

## Agent Run 工具调用验证

前置条件：后端已配置可调用模型，且 `lookup_profile` 内置工具可用。

1. 创建一次要求调用已注册工具的 run：

```bash
curl -sS -X POST http://127.0.0.1:8090/api/agent/runs \
  -H 'Content-Type: application/json' \
  -d '{
    "goal": "Use the profile lookup tool, then summarize the user profile.",
    "supplement": {"data": {"user_id": "u1001"}},
    "tools": [{
      "type": "function",
      "function": {
        "name": "lookup_profile",
        "description": "Look up a user profile.",
        "parameters": {
          "type": "object",
          "properties": {"user_id": {"type": "string"}},
          "required": ["user_id"]
        }
      }
    }],
    "tool_choice": "required",
    "disable_fast_path": true
  }'
```

2. 验证响应：

- `status` 为 `completed`
- `tool_calls[0].id` 非空，`type` 为 `function`
- `tool_results[0].tool_call_id` 等于 `tool_calls[0].id`
- `messages` 顺序包含 assistant tool call、对应 tool message 和 final assistant message
- `output` 包含最终回答，且没有把工具结果误当成 assistant 文本拼接

3. 使用返回的 `run_id` 请求 `/api/agent/runs/:runID/trace`：

- 至少存在一条 `trace_type=tool_call`
- trace safe labels 中的 `tool_call_id` 与响应一致
- trace payload 可以包含 argument keys / rune counts，但不得包含原始 `user_id` 值或 raw tool result

## 失败排查

- 若 `healthz` 失败，先检查后端端口、配置环境变量和数据库连接。
- 若 smoke 返回鉴权失败，检查是否配置了 control-plane token，并通过 `--control-plane-token` 传入。
- 若 foundation 计数为 0，检查 runtime bootstrap 是否执行，以及数据库 schema 是否指向正确 search path。
- 若 System Truth lifecycle 计数为 0，检查 system resources sync 是否已按 active truth 生成 source、draft、compile 和 active pointer。
- 若 projection boundary 失败，检查写入端是否仍使用非 `runtime_projection.*` schema、业务 EvidenceRecord-like kind，或把 `materialization_target.core_materialization_scope` 改成了非 `projection_candidate_only`。
- 若 checkpoint readout 为空，先确认目标 run 是否产生等待态或 checkpoint ref；空 `items` 是允许的 fallback，但字段中不能出现 raw payload 或 resume token。
- 若 DOM smoke 失败，先确认 Web 控制台能打开 System Validation tab，再检查 `data-testid` 是否被移除或重命名。
- 若 Playwright 启动失败，重新安装 Python Playwright 浏览器依赖。
- 若 Agent Run 返回工具未注册，确认 declaration name 与 Athena registry 一致；业务远程工具需要等待 issue `#9` 的 registry/execution surface。
- 若 `tool_choice=required` 仍未产生调用，检查模型提供方是否支持标准 tool choice，并查看 model callback 与 canonical tool trace。
